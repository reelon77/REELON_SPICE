## 三、已达成的核心决策（不要推翻，除非用户提出）

1. **新项目选定：迷你 SPICE 电路仿真器**。理由：一个项目同时命中"数学（数值方法）+ C++ + EDA（电路仿真）"，是华大九天模拟 EDA 产品线的微缩版，最能把用户"数学→EDA"的桥搭起来。
2. **项目定位**：LSM-Tree 深挖成旗舰；SPICE 作为"数学→EDA"的直接证据；Hazel 降级处理或转化用途（见第 5 点）。
3. **架构：三层求解器嵌套**——瞬态(时间步进) 包 牛顿(非线性) 包 LU(线性)；器件库统一 `stamp()` 接口做多态。开发顺序 = 从内层往外逐层包壳。
4. **优先级铁律**：**内核第一**（解析器→MNA→LU→牛顿→瞬态 + 正确性验证），可视化前端只是第 4 周有余量才做的 polish。宁可"扎实内核 + Python 画图"，不要"半吊子内核 + 花哨界面"。
5. **Hazel 的处理**：用户已集成 **ImGui**（关键 enabler）。可选方案是第 4 周用其 ImGui + 渲染能力做 SPICE 的**交互可视化前端**，把 Hazel 从"教程跟练未完结"转为"自研框架 + 原创可视化工具"。但**内核与引擎代码解耦**：SPICE 编译成独立库，引擎只做显示，内核绝不反向依赖引擎。**面试勿称 Hazel 为"完整游戏引擎"**（无 ECS/场景系统，会露馅），如实说"OpenGL+ImGui 应用/渲染框架"。
6. **诚信红线（贯穿）**：开源实现**只读思路、看结构，绝不抄代码**。参考架构可讲、可坦白说"参考了 X 的设计"；复制粘贴讲不清取舍会当场露馅且是诚信问题。姿势 = 读懂→关掉→自己重写→能解释每一行。
7. **投递策略**：**最小可展示版本先投，再迭代升级**。第 1 周末（纯电阻电路跑通）项目即够格上简历，立即开投抢提前批尾声，别等全做完。
8. **验证方式**：解析解（手推标准答案，主打，秀数学）为主 + ngspice/LTspice 对拍（复杂电路）+ 边界用例，用 Google Test 组织自动化。
